-- 02 · dimensional modeling

Facts are events. Dimensions are their context.

A second, purpose-built schema you build alongside the normal tables — when the question shifts from “record what happened” to “summarize everything so far.”

Source: lecture-04-notes.md, Part 2; Kimball Group, “Star Schemas and OLAP Cubes”; Wikipedia, “Star schema”
The fact table is narrow and long: numbers plus keys. The dimensions are wide and short: labels. You add up facts; you group and filter by dimensions.
-- 02 · grain
“One row = one order.”
The grain is the one-sentence definition of what a single fact row is — decided before anything else. Get it wrong (one row per line item, by accident) and every aggregate on top silently means something else.
Source: lecture-04-notes.md, Part 2; Kimball Group, “Grain”
Kimball calls declaring the grain 'the pivotal step in a dimensional design'. Everything else — which dimensions, which measures — has to agree with that sentence. Grain returns in Part 4 as the fan-out trap.
-- 02 · build tricks

dim_date: generated once, not every query

CREATE TABLE dim_date AS SELECT d::date AS dateKey, EXTRACT(quarter FROM d)::int AS quarter, EXTRACT(month FROM d)::int AS month, to_char(d, 'Mon') AS monthName, EXTRACT(isodow FROM d)::int AS dayOfWeek, to_char(d, 'Dy') AS dayName FROM generate_series(DATE '2024-01-01', DATE '2024-12-31', INTERVAL '1 day') AS d;
366
rows — every day of 2024, a leap year. Sundays included, though the shop is closed.

› quarter, month, day name: computed once, stored as columns

› no query ever works out “what quarter is this?” again

Source: lecture-04-demo.sql, Part 6 (CREATE TABLE dim_date → SELECT 366); Kimball Group, “Calendar Date Dimensions”
Calendars are cheap to precompute and expensive to keep recomputing. A date dimension lists every day, not only the days something happened. Kimball: calendar date dimensions are attached to virtually every fact table.
-- 02 · build tricks

Make “missing” a value, not an absence

INSERT INTO dim_employee VALUES (0, '(online)', 'Online', '(none)');

and in the fact-table build:

coalesce(o.employeeID, 0) AS employeeKey

› online orders have no employee: employeeID IS NULL

› row 0 gives them one — every fact row now has a valid, non-null employee key

› every join to dim_employee is ordinary, never a “what if it’s NULL” case

Part 6 of the demo never needs LEFT JOIN against dim_employee. Plain inner joins lose nothing.
Source: lecture-04-demo.sql, Part 6; lecture-04-notes.md, Part 2; Kimball Group, “Nulls in Fact Tables”
Why this avoids LEFT JOIN: an inner join drops a row only when it finds no partner. With the unknown member, every fact row's employeeKey (0 for online) matches a real dim_employee row, so the inner join keeps all 600. Compare Part 4: the same inner join against raw employees keeps 419 of 600. Kimball: avoid nulls in fact-table foreign keys; use a default dimension row.
-- 03 · star

-- 03 · snowflake

Snowflake: a dimension split into sub-tables

Source: lecture-04-notes.md, Part 3 (the dim_category / dim_brand example); Kimball Group, “Snowflaked Dimensions”
dim_product normalized into dim_product + dim_category + dim_brand, each joined in turn. Revenue by category is now two hops from the fact. The other dimensions stay flat: snowflaking is per dimension. This split is the notes' example; the demo builds only the star.

Less redundancy, more joins

Snowflaking buys less redundancy and costs more joins and more tables to navigate — a bad trade most of the time. Wikipedia adds that dimension tables are small next to the fact table, so the space saved is often negligible.
-- 03 · the default
Star by default. Snowflake only as the exception — with a specific, concrete reason.
“We generally encourage you to handle many-to-one hierarchical relationships in a single dimension table rather than snowflaking.” — Kimball Group, Design Tip #105
Source: Kimball Group, Design Tip #105, “Snowflakes, Outriggers, and Bridges” (2008)
Kimball's reasons: snowflakes are harder for business users to navigate and can hurt query performance; a flat dimension holds the same information. Outriggers are 'acceptable in moderation' but 'the exception rather than the rule'. The notes' example reason is a huge dimension; Kimball himself calls the storage savings minimal.

-- 04 · the thesis
A join is: pair every row of A with every row of B, then keep the pairs you want.
Every join type is a variation on two questions: which pairs do we keep, and what do we do with the rows that found no pair?
Source: lecture-04-notes.md, Part 4.0
That's genuinely it. CROSS JOIN isn't a weird separate thing — it's the whole Cartesian product before anything is thrown away. We start there.
-- 04 · step 1 of 3

CROSS JOIN: every row × every row

SELECT count(*) FROM orders CROSS JOIN customers;
18,000
rows = 600 orders × 30 customers. Every possible pairing — most of them nonsense.

PostgreSQL defines A CROSS JOIN B as exactly A INNER JOIN B ON TRUE: a join whose condition can never fail.

Source: lecture-04-demo.sql (18000); PostgreSQL 16 docs, “Joined Tables” (CROSS JOIN ≡ INNER JOIN ON TRUE; N × M rows)
Guess before running it. No order belongs to all 30 customers — this is every possible pairing, the raw material every other join is carved out of. The grid zooms in on 3 orders × 3 customers.

-- 04 · aliasing

Two tables, one column name: ambiguous

SELECT orderID, customerID, firstName FROM orders JOIN customers ON customers.customerID = orders.customerID WHERE orderID = 1001;
ERROR: column reference "customerid" is ambiguous

› customerID exists in both tables; the engine refuses to guess — even though the values are equal on every joined row

› fix: alias and qualify — FROM orders o JOIN customers c, then o.customerID

Source: lecture-04-demo.sql, Part 3 (error text from running it); lecture-04-notes.md, Part 4.3
Error on purpose — read the message aloud. The rule is about names, not values. Habit: in any multi-table query, prefix every column.
-- 04 · aliasing

An alias doesn’t add a nickname — it replaces the name

SELECT orders.orderID FROM orders o WHERE o.orderID = 1001;
ERROR: invalid reference to FROM-clause entry for table "orders" HINT: Perhaps you meant to reference the table alias "o".

Once you write FROM orders o, the name orders stops existing for the rest of the query. PostgreSQL’s hint tells you exactly what happened.

Source: lecture-04-demo.sql, Part 3 (error and hint text from running it); lecture-04-notes.md, Part 4.3
Error on purpose. The HINT is PostgreSQL telling you the fix. Same idea returns in self-joins, where aliases are the only way to tell two copies of one table apart.
-- 04 · shorthand

USING is shorthand. NATURAL JOIN hides the condition.

SELECT customerID, c.firstName, o.orderID FROM orders o JOIN customers c USING (customerID) WHERE o.orderID = 1001;

USING (customerID) = ON o.customerID = c.customerID, and the column appears once in the output.

SELECT count(*) FROM orders NATURAL JOIN sales;
97
rows — both tables hold the same 600 sales
NATURAL JOIN joined on all 12 shared column names — deliveryDate and rating among them. NULL = NULL is not true, so rows with a NULL there vanished. And it changes silently the day either table gains a matching column. Never use it in real code.
Source: lecture-04-demo.sql, Part 3 (97); PostgreSQL 16 docs, “Joined Tables” and “Comparison Functions”
The two tables share twelve column names; all twelve had to be equal. Only online orders that also got a rating survive: 97. The PostgreSQL manual calls NATURAL 'considerably more risky' than USING. Takeaway: the join condition should always be visible in the code you're reading.

-- 04 · the most important trap

WHERE vs. ON: it depends on when each runs

ONWHERE
runswhile deciding what matches — before NULL-paddingafter the whole join, NULL-padding included
inner joinsame resultsame result
outer joinkeeps the unmatched rowscan delete the NULL-padded rows — LEFT becomes INNER

A WHERE that mentions the right-hand table after a LEFT JOIN should make you stop and ask: am I filtering matches, or un-inviting the rows my LEFT JOIN was supposed to protect?

Source: lecture-04-notes.md, Part 4.7; PostgreSQL 16 docs, “Joined Tables” (ON vs. WHERE)
The PostgreSQL manual: a restriction in ON is processed before the join, one in WHERE after the join — 'That does not matter with inner joins, but it matters a lot with outer joins.'

-- 04 · the fan-out trap

One customer value, copied onto every order row

› customers.moneySpent is one number per customer — customer grain

› orders has many rows per customer — order grain; the join copies moneySpent onto every one: not divided, not split, copied whole

Source: lecture-04-demo.sql, Part 5; customers.moneySpent and order counts (Aram Vardanyan: 40 orders)
Aram placed 40 orders, so his 13,544.72 is summed 40 times. Do that for every customer and you get 4,079,958.38. After this join the result has one row per order, not one per customer.

the fix, in general

› aggregate the fine-grain table first, then join the result back — one row per customer

-- 04 · the fan-out trap
“Is the thing I’m summing at the same grain as the rows I’m joining through?”
If not: am I about to sum the same value multiple times?
Source: lecture-04-notes.md, Part 4.10
Ask it every time you aggregate after a join. It's the grain from Part 2, applied to a query instead of a schema.

-- 04 · bridge
A document is a join you saved.
A denormalized JSON document is the materialized result of a one-to-many join. The relational model keeps the pieces separate and joins on demand; the document model pre-joins once and stores the result. Same information — a different point where the join cost is paid.
Source: lecture-04-notes.md, Part 4.12; lecture-04-demo.sql, Part 5 (jsonb_agg query)
The demo builds one JSON document per customer with jsonb_agg: all of Diana's orders nested inside her customer object. Fast to read; keeping it right when Diana moves is the application's problem.
-- 04 · losslessness

A runnable proof that nothing was lost

SELECT o.orderID, o.orderDate, o.orderTime, …, p.brand, p.price, p.cost FROM orders o JOIN customers c ON c.customerID = o.customerID JOIN products p ON p.productID = o.productID LEFT JOIN employees e ON e.employeeID = o.employeeID EXCEPT SELECT * FROM sales;
0 rows
in both directions

Rebuild the flat file from the four tables, subtract the original: nothing left over. Swap the halves: nothing again. That’s lossless-join decomposition — as a query you can run, not a theory term.

Source: lecture-04-demo.sql, Part 4 (0 rows); PostgreSQL 16 docs, “Select Lists”
The full SELECT lists all 29 columns of sales. The LEFT JOIN to employees matters, or the web shop is lost. EXCEPT treats two NULLs as equal (the manual states that rule for DISTINCT; the 0-row result shows EXCEPT does the same).
-- 04 · myth

GROUP BY a, b = GROUP BY b, a

GROUP BY c.customerID, c.firstName, c.lastName
GROUP BY c.lastName, c.firstName, c.customerID

→ the same groups, the same totals

› a group is defined by the combination of values in the listed columns — order changes nothing

› if a total looks wrong, GROUP BY order is not the place to look — check for a fan-out first

Source: lecture-04-notes.md, Part 4.14; PostgreSQL 16 docs, “Table Expressions: GROUP BY”
PostgreSQL: GROUP BY groups together the rows that have the same values in all the columns listed. 'All the columns listed' is a set, not a sequence. Output order comes from ORDER BY. steps/15-group-by-order.sql proves it with EXCEPT → 0 rows.

None of them threw an error. All three returned a table that looked completely normal. SQL correctness bugs are almost always silent — and an AI assistant will write a plausible, syntactically perfect join whether the logic is right or not.

Nothing turns red. The query runs, returns rows, and is simply wrong. That's the whole point of this lecture.
