Part 2 · Data Modeling

First name? First + last? Not enough.

  • ✕ First name? Obviously not.
  • ✕ First + last name? Two people can both be "Anna Sargsyan."
  • First + last + birthDate? Now it's probably unique — a composite natural key, three attributes doing the job of one.
  • But it's fragile: three columns to carry everywhere, one typo breaks the link, and it still isn't guaranteed unique.
Real systems go furtherRecord linkage, fuzzy matching, probabilistic dedup — entire techniques exist just to decide "is this the same person?" Out of scope today; the honest answer is that even our three-column key is a bet, not a proof.
Say This fragility is exactly what shows up in Part 5's JOIN — three columns, all of them have to match. If someone asks "what if two people share all three?" — that's the record-linkage story: hospitals tune for zero wrong merges, marketing tunes the opposite way; same code, opposite thresholds, and nothing in SQL tells you which. Mention it, move on.
So we invent customerID.
One small integer. Means nothing outside the database. Never changes. A surrogate key — the PK you saw on CUSTOMERS in the diagram.
Say Now you know why it's there, not just that it is. Real systems assign it at signup — identity is recorded, never reconstructed.
Part 2 · Optional aside

moneySpent: stored, or computed?

  • It's the sum of that customer's orders — the database can compute it any time.
  • Storing it means every new order must also update it.
  • If that update ever fails, the stored number silently disagrees with reality.
Trade-off
  • Stored: fast to read, can drift
  • Computed: always correct, costs a JOIN
Say Skip if short on time — it pays off in Part 7, not load-bearing right now.

Part 2 · Data Modeling

A → B: A determines B

Attribute A functionally determines attribute B if every value of A is associated with exactly one value of B.

orderID → orderDate -- one order, one date orderID → customerFirstName -- the key determines everything (firstName, lastName, birthDate) → moneySpent -- the interesting one

The first two are trivial — orderID is the key, so of course it determines the row. The third one is the point: moneySpent depends on which customer this is, not which order. That's a dependency between non-key columns, and it's what normal forms give you a name for.

Say orderID trivially determines the whole row. The dependencies worth noticing are between the other columns.
orderID → (firstName, lastName, birthDate) → moneySpent
moneySpent depends on which customer this is — not on the order. Key → non-key → another non-key: that's a transitive dependency, and it's the whole mechanism behind Part 1's redundancy.
Say Same chain exists for every employee and product attribute too.
Part 2 · Normal Forms

1NF — one value per cell

A normal form is a rule a table either satisfies or doesn't, each aimed at one kind of redundancy. The first rule: every cell holds exactly one value — no lists, no repeating groups.

Breaks 1NF — a multi-item order squeezed into one row

Two values in one cell. You can't filter, count or join on "Keyboards" — it's trapped inside a string.

Fixed — one row per value

Notice the cost: orderID alone no longer identifies a row. The key became (orderID, productCategory) — a composite key. That's what 2NF is about.

Each form fixes the previous one's leftover: 1NF's fix creates composite keys (2NF's problem); 2NF's fix leaves non-key columns depending on each other (3NF's problem). Most real schemas stop at 3NF.

Part 3 · Why SQL

Splitting the data created a new problem

One business question now needs data pulled correctly from four places at once, every time — without writing a loop by hand.

  • "Show me this month's receipts" now means: find the order, look up its customer, its employee, its product — separately.
  • Do that by hand in Python or Excel and you're rebuilding a query engine, badly.
That language is SQLDefines the tables, fills them, and recombines them on demand.
Say This motivates SQL as a consequence of modeling, not a separate topic. If someone asks "why split at all if a JOIN puts it back?" — splitting isn't about reading, it's about writing: fixing a birth date is one statement here, 42 in the flat file.

Part 4 · DDL

Stored as text, price sorts wrong

Text sorts character by character, not by value — this is why price is DECIMAL, never text.

As text — ORDER BY price
'100.00'
'52.00'
'9.99'
As DECIMAL — ORDER BY price
9.99
52.00
100.00
Same logic, everywhere0.1 + 0.2 is exactly 0.3 — only if the type promises it. That's why money is DECIMAL and never a float, anywhere in this schema.
Say Run it live: SELECT unnest(ARRAY['9.99','52.00','100.00']) ORDER BY 1. 100 sorts before 52 sorts before 9.99 — the opposite of numeric order.
Part 4 · DDL · Caveats

Two things that surprise people

Naming
PostgreSQL folds unquoted identifiers to lowercase — customerID becomes customerid in every output, every error message, every \d.
VARCHAR vs TEXT
They perform identically in PostgreSQL — no speed difference, no storage difference. The length in VARCHAR(50) is a constraint you're choosing, not an optimization you're making.
Say Neither of these is a bug — both surprise almost everyone the first time.
Part 4 · DDL · Caveats

Order matters. IDs aren't yours to give.

Creation order
A referenced table must exist before the table that references it — customers, employees and products before orders. Try it backwards and read the error.
SERIAL
Generates ids for you. You never INSERT a customerID — the database assigns the next one, and you find out what it was by asking, not by guessing.
No gaps? No.
A failed or rolled-back insert still consumes its number. SERIAL ids are unique, not consecutive — never assume the max id equals the row count.
Say Try creating orders first — the error you get is the lesson. The gaps point pre-empts the question someone always asks in week 6.
Part 4 · DDL

Six words, six promises

ConstraintWhat it promises
PRIMARY KEYUniquely identifies a row. Never null, never duplicated — one per table, and what foreign keys point at.
REFERENCESThis value must already exist in the other table.
UNIQUENo two rows may share this value. Unlike PRIMARY KEY: many per table, and NULLs allowed.
NOT NULLThis fact is required.
CHECKA rule you invent, enforced on every write.
SERIALAuto-incrementing — the database generates the id.
Say These six words are doing all the work in the "Business Impact" line from Lecture 1. If asked why birthDate is nullable but firstName isn't: you can't have a customer without a name; you can have one whose birth date you don't know. NOT NULL means "the business can't function without this."
Part 4 · DDL

One reference, enforced

A foreign key is a promise the database checks on every write. Notice what's not here: no customer name, no category, no price — only ids.

CREATE TABLE orders ( orderID INT PRIMARY KEY, customerID INT NOT NULL REFERENCES customers(customerID), employeeID INT NOT NULL REFERENCES employees(employeeID), productID INT NOT NULL REFERENCES products(productID), orderTotal DECIMAL(10,2) CHECK (orderTotal >= 0), orderDate DATE NOT NULL );
Say Point at REFERENCES — this one word is what makes an impossible order impossible. Each fact lives in exactly one place — the same FK lines from the ER diagram. Why is orderID INT here and SERIAL elsewhere? Because the ids already exist in the source file; we keep them rather than invent new ones.

Part 5 · DML

By hand, one row at a time

Bulk-loading from sales_raw is the special case — these three are the everyday statements.

-- one row by hand; RETURNING prints the new id INSERT INTO products (category, price) VALUES ('Tablets', 499.00) RETURNING productID; -- several rows, one statement INSERT INTO products (category, price) VALUES ('Webcams', 59.00), ('Printers', 189.00);
-- change one row; without WHERE, EVERY row UPDATE products SET price = 459.00 WHERE category = 'Tablets'; -- remove them again DELETE FROM products WHERE category IN ('Tablets','Webcams','Printers');
RuleWhy
Name the columnsNever rely on column order — it breaks the moment a column is added.
Skip SERIAL columnsThe database fills them. RETURNING tells you what it chose — you don't guess.
Quote text and dates, never numbers'Tablets', '2024-08-27', but 499.00.
WHERE on UPDATE and DELETEWithout it, every row changes — and there is no undo outside a transaction.
Parents before childrenINSERT the customer before the order; DELETE the order before the customer. The foreign key enforces both directions.
Say Runs at any point after Part 4 — even on empty tables, since products has no parent. RETURNING is the answer to "how do I know which id it got?". The DELETE at the end leaves products exactly as it was, so the 42/8/4/6/42 check later is untouched. Point out the missing WHERE joke: UPDATE without WHERE repriced the whole catalogue.
Part 5 · DML

DISTINCT: 42 rows become 8

INSERT INTO customers (firstName, lastName, birthDate, moneySpent, anniversary) SELECT DISTINCT customerFirstName, customerLastName, customerBirthDate, customerMoneySpent, customerAnniversary FROM sales_raw; -- 42 rows in, 8 rows out

Same pattern fills employees (4 rows) and products (6 rows) — but sales_raw has no customerID column at all, only names. Translating a name into an id is next.

Say Parents first, children last — try inserting into orders first if you want to see why. Forget DISTINCT and you get 42 customers: the redundancy survived and nothing was gained.
Part 5 · DML

Translating names into ids

INSERT INTO orders (orderID, customerID, …, orderTotal, orderDate) SELECT r.orderID, c.customerID, …, r.orderTotal, r.orderDate FROM sales_raw r JOIN customers c ON c.firstName = r.customerFirstName AND c.lastName = r.customerLastName AND c.birthDate = r.customerBirthDate -- …then the same JOIN shape for employees and products

All three columns of the natural key, matched — the fragility from Part 2, now visible in code. Full statement runs in the terminal.

Say This is the question someone always asks — "why not just keep the columns from sales_raw?" This is the answer. All this ceremony exists only because the source file has no ids; if it did, this would be a plain INSERT … SELECT.
Part 5 · DML

Checking your work: 42 / 8 / 4 / 6 / 42

SELECT 'orders', count(*) FROM orders -- expect 42 UNION ALL SELECT 'customers', count(*) FROM customers; -- expect 8
If orders isn't 42The join is wrong somewhere — this is the most common mistake at this step, and the row count is how you catch it. Fewer than 42: a name didn't match. More than 42: two customer rows matched the same name.

Part 7 · The Payoff

Three JOINs, one row per order

SELECT o.orderID, c.firstName, p.category, o.orderTotal FROM orders o JOIN customers c ON c.customerID = o.customerID JOIN products p ON p.productID = o.productID JOIN employees e ON e.employeeID = o.employeeID ORDER BY o.orderDate; -- 42 rows — exactly the file you started with

This is the exact inverse of the split in Part 5 — same shape, reversed. Splitting is lossless.

Say But now there's one place to fix a birth date, one place to change a price.
Part 7 · The Payoff

Is the stored number still true?

SELECT c.firstName, c.moneySpent AS stored, SUM(o.orderTotal) AS computed FROM customers c JOIN orders o ON o.customerID = c.customerID GROUP BY c.customerID, c.firstName, c.moneySpent;

Part 9 · ALTER TABLE

Changing your mind safely

  • Add a column with no DEFAULT — every existing row gets NULL.
  • Can't add NOT NULL while NULLs exist — backfill first, then it works.
  • Rename a column, widen a VARCHAR — both safe. Shrinking can fail if data doesn't fit.
  • Add a named CHECK constraint after the fact — same vocabulary as Part 4.
ALTER TABLE orders ADD COLUMN channel VARCHAR(20); ALTER TABLE orders ALTER COLUMN channel SET NOT NULL; -- ERROR: contains null values ALTER TABLE orders ADD CONSTRAINT channel_known CHECK (channel IN ('in_store','online'));
Say Run the SET NOT NULL failure live, then backfill and retry — read the real error both times.
Part 9 · DELETE / TRUNCATE / DROP

Three ways to make data disappear

StatementRemovesTable survives?
DELETE FROM t WHERE ...Matching rowsYes
TRUNCATE tEvery rowYes, empty
DROP TABLE tThe table itselfNo

All three refuse to run if another table still points at this one — try each against products live. Every refusal is the foreign key doing exactly what Part 4 promised.

Say DELETE, then TRUNCATE, then DROP TABLE — same error family, three different statements. If asked "why doesn't it just delete the orders too?" — ON DELETE CASCADE does exactly that, and it isn't the default because silently deleting financial records is usually a disaster.
Part 9 · A common misconception

CASCADE doesn't delete your data

DROP TABLE products CASCADE reads like "delete everything that pointed at it." It doesn't.

DROP TABLE products CASCADE; -- NOTICE: drop cascades to constraint -- orders_productid_fkey on table orders
What actually happensCASCADE drops the dependent constraint on orders — not orders itself, not its rows. orders survives, just unchecked: every productID now points at nothing. Demo this on a disposable pair of tables, never the real schema.
Say Demo this on scratch_categories/scratch_items, never on the real schema. Insert one row first so the survivor visibly has data pointing at nothing — that's the state the foreign key existed to prevent.
Part 9 · Recap

Every refusal today was on purpose

  • ALTER added, renamed, retyped and constrained a column — then undid all of it.
  • DELETE / TRUNCATE / DROP all refused to touch a row or table another table still points at.
  • CASCADE overrides that refusal deliberately — dropping the constraint, never the data, unless you also name the dependent table.

Summary

What today actually built

  • Redundancy causes update, insertion and deletion anomalies.
  • Model first: entities, relationships, cardinality, an ER diagram.
  • Composite natural key works but is fragile — invent surrogate ids.
  • A transitive dependency is a 3NF violation — that's what redundancy is.
  • SQL is declarative: DDL defines, DML changes, DQL reads.
  • Primary key identifies · foreign key connects · constraints enforce.
  • Splitting is lossless — JOIN rebuilds the original view.
  • ALTER evolves a schema; DELETE/TRUNCATE/DROP all respect foreign keys.
